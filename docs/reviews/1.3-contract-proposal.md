# Barba-CV 1.3: limited contract proposal for maintainer review

**Historical status at authoring: unapproved proposal for [issue #30](https://github.com/Eurobotics-Association/barba-cv/issues/30). No 1.3 contract, validator, template, conversion or release has been implemented.** Read the [field comparison]({{ '/docs/reviews/1.3-historical-comparison.html' | relative_url }}) first. PR #29 merged the historical archive into `main`; this proposal does not replace or duplicate those files.

## Recommended boundary

Make 1.3 a narrow clarification and repair release. Keep the CV at the root, keep the established broad sections and free-text dates, keep only the version declaration mandatory, and leave application-specific rules to applications. A 1.3 writer should emit one documented shape per field; a compatibility reader may accept separately documented legacy shapes and report which versions fit. That distinction matters because the current 1.2 template and examples conflict.

The historical 1.0 template and published 1.2 files remain immutable. Corrected validation artifacts must be new, version-specific files with provenance. A 1.3 payload example is not a validator. JSON syntax, JSON Schema validity, payload conformance and backward compatibility are separate claims.

## Preserve unchanged

- Root CV sections: `personal_info`, `profile_summary`, `experiences`, `education`, `skills`, `certifications`, `languages`, `interests`, and the existing 1.2 `position_sought`, `project_achievements`, `meta` and `extensions` concepts. Do not wrap the CV in a new envelope.
- Common text fields for names, contact, organizations, roles, qualifications, dates and descriptions where the 1.0 template, 1.2 template and current examples agree. Keep dates human-readable; add no mandated country, postcode, date format, demographic field or profession-specific key.
- Sparse payloads: no new required CV content fields. Absence, empty text, empty arrays and null need field-level documentation; they are not interchangeable without an explicit rule. Do not require every example-template placeholder in real payloads.
- Project content under an ordinary standard section, not hidden in `extensions`. Do not add rendering or CV-selection data.

## Clarify documentation without changing semantics

1. State what belongs in the data standard, example templates, formal validators and stricter application profiles. The 1.0 artifact is a template, not a JSON Schema validator.
2. Explain `meta` as processing metadata and `extensions` as an optional object for adopter-specific keys. For example, `"extensions": {"vendor.example.reference": "A-42"}`. A consumer that does not understand a particular extension can ignore its meaning; a pass-through consumer should preserve it unchanged. Unknown extension content must not authorize an application action. Standard CV fields belong in standard locations. The exact validator rule for `extensions` needs decision D2 below.
3. Correct integration links: `docs/llm-integration.md` names nonexistent `examples/barba-cv.example.json` and `docs/barba-cv-schema-reference.md`. Link to the actual template and the agreed new reference after publication.
4. Explain declared version versus structural compatibility. A missing declaration does not prove 1.0. A declared `1.2` does not prove conformance. Report ambiguous matches, field-level mismatches and unsupported structures.
5. Avoid claims that objects, strings or arrays improve storage, compression or search without measured evidence. No benchmark is available here.

## Repair defective validation encoding, subject to the agreed field policy

- Publish a **new derived 1.2 validator** only if useful for reading old data; retain the exact published 1.2 schema. Label it a repair with its provenance and limitations. The current schema references eight absent definitions, rejects its own template's `extensions`, and accepts any version string.
- Publish a separate strict 1.3 validator after decisions D1–D6. All references must resolve. A strict 1.3 check should require `barba_cv_version` to be exactly `"1.3"`, validate the agreed field shapes, and reject unrelated root keys while allowing the agreed `extensions` behavior. `$defs` and `$ref` are optional implementation details, not payload requirements.
- Keep version detection separate from strict validation. A diagnostic tool should return declared version, structurally compatible versions, conflicts, ambiguity and unsupported data. It must not rewrite input. Any conversion must be a separate explicit operation with a new output and loss/ambiguity report. Software release version and payload format version are separate.

## Decisions with semantic or compatibility impact

The recommendations below are proposals. Reader compatibility means a newer compatibility reader consuming older data; writer compatibility means an older reader consuming new output. Neither is guaranteed by the label “1.3.”

### D1. Version declaration

**Problem:** Published 1.2 validation accepts arbitrary text, so even `"future"` appears valid. The 1.0 original has no declaration.

Before: `{"barba_cv_version":"future","profile_summary":"..."}`. Proposed strict 1.3 output: `{"barba_cv_version":"1.3","profile_summary":"..."}`.

**Benefit:** clear version-specific validation and dispatch. **Cost:** strict 1.3 rejects undeclared or mislabeled old payloads. A compatibility reader should still inspect their structure and report mismatches. An old 1.2 reader requiring a version string might accept `"1.3"` superficially, but that says nothing about its support for 1.3 fields. **Conversion:** adding a declaration cannot be automatic proof of shape; only emit it after validating or explicitly converting. **Recommendation:** approve exact `1.3` in strict 1.3 output, with structural detection separate.

### D2. Optional extensions

**Problem:** The 1.2 template includes `extensions: {}`, but its schema rejects the field. Its intended purpose is adopter-specific keys.

Before: `{"barba_cv_version":"1.2","extensions":{"vendor.example.reference":"A-42"}}` is rejected by the published schema. Proposed 1.3: `{"barba_cv_version":"1.3","extensions":{"vendor.example.reference":"A-42"}}`, with the object optional and contents unconstrained by the core standard.

**Benefit:** genuine extensibility without altering standard field names. **Cost:** consumers cannot assume arbitrary extension content is meaningful or safe for their own application. A strict old reader can reject the added root property; current example-based writers already include it. **Conversion:** preserve unknown extension values byte-for-byte at the JSON data level when round-tripping; report if a target format cannot hold them. **Recommendation:** approve optional object, arbitrary adopter keys, ignore unknown meaning, preserve on pass-through. Do not create a registry or namespace mandate in 1.3.

### D3. Skills item form

**Problem:** The original 1.0 template has empty arrays, which do not establish item types. The published 1.2 template uses objects, while all three current example CVs use text for populated skills.

Before, 1.2 template: `"it_skills":[{"name":"Python","level":"advanced","category":"tool","keywords":[]}]`. Before, observed payload style: `"it_skills":["Python"]`. Proposed canonical 1.3 writer: `"it_skills":["Python"]` (likewise hard and soft skills).

**Benefit:** smallest observed form, compatible with populated repository examples. **Cost:** an object carries `level`, `category` and `keywords` that a string cannot hold. A new reader can support strings and separately recognize legacy 1.2 objects; an old object-only reader may reject new strings, while an old string-only reader already rejects the 1.2 template. **Conversion:** object → string loses metadata unless it is preserved in an explicit separate output; do not silently reduce it to `name`. **Recommendation:** use strings for 1.3 writing; compatibility readers report object-form input, and defer automatic object-to-string conversion until loss handling is agreed.

### D4. Education location

**Problem:** `school_location` is text in the original 1.0 template, but `{city,country}` in the published 1.2 template and current examples.

Before: `"school_location":"North campus, Greater Paris"`. Proposed canonical 1.3 writer where components are known: `"school_location":{"city":"Paris","country":"France"}`.

**Benefit:** preserves the already-published 1.2 shape and makes known components queryable. **Cost:** the old free-text shape may contain campus or region information with no destination in `{city,country}`. A new compatibility reader can recognize both; an old text-only reader rejects an object, and an old object-only reader rejects a text value. **Conversion:** never split or discard free text by guess. Report unresolved conversion; if a later raw-text field is agreed, preserve it there. **Recommendation:** retain object for strict 1.3 output; accept old text only in compatibility reading, not as an undocumented union in strict output.

### D5. Project names and field forms

**Problem:** The root key was renamed, and the published 1.2 template turns six structured fields into text while the three example CVs retain structured period and arrays. The original 1.0 template and three repository examples use object periods, array-shaped list fields, and object `synonyms`, but the empty 1.0 arrays and objects leave item and key semantics uncertain.

Before, 1.2 template: `"project_achievements":[{"period":"2020–2022","role":"lead","sectors":"health","competencies":"planning","keywords":"migration","synonyms":"modernization"}]`. Proposed 1.3 writer: `"project_achievements":[{"period":{"start":"2020","end":"2022"},"role":["lead"],"sectors":["health"],"competencies":["planning"],"keywords":["migration"],"synonyms":{}}]`.

**Benefit:** matches the repository example shapes for period and list fields; permits multiple values without delimiters. **Cost:** the published template's text values, especially `period`, may not split unambiguously. An old string-only 1.2 reader can reject new structured values. A new compatibility reader can recognize and report both shapes, but strict 1.3 output would have one shape. **Conversion:** a text period such as `"early 2020s"` cannot be split faithfully; comma-separated lists and free-text synonyms may not have safe mappings. Report ambiguity and retain original input if no agreed mapping exists. **Recommendation:** approve structured period and, as a new explicit rule, text items in role/sectors/competencies/keywords lists. Do not attribute that item rule to the original empty arrays. The 1.2 template conflicts with both the original and current examples. Decide whether `synonyms` remains an opaque object or is deferred from strict writing until a populated reference establishes its semantics. Do not silently convert any project text.

### D6. Renames and historically omitted data

**Problem:** 1.0 has `Middle_name`, `street2`, `instagram`, `facebook`, `X/twitter`, root `parsing_errors`, and `projects_achievements_extracts`. Published 1.2 has `middle_name`, `twitter`, `meta.parsing_errors`, `project_achievements`; the other old fields are absent.

Before: `{"personal_info":{"Middle_name":"A","address":{"street2":"Unit 4"},"links":{"instagram":"https://example.org/i"}},"parsing_errors":[]}`. Proposed 1.3 canonical names: `middle_name`, `meta.parsing_errors`, `project_achievements` and `twitter`; optional `address.street2`, `links.instagram` and `links.facebook` are under consideration.

**Benefit:** one spelling and placement for canonical writes, with optional restoration preventing loss of old address/social information. **Cost:** old readers can ignore or reject new names; 1.2 consumers may not expect restored fields. **Conversion:** alias `Middle_name` only when no conflicting `middle_name` value exists; keep both and report conflict otherwise. `X/twitter` → `twitter` needs confirmation that the semantics match. Root `parsing_errors` → `meta.parsing_errors` needs conflict handling if both exist. Unknown social-link item structure in `other_socials` makes automatic mapping unsafe. **Recommendation:** keep published 1.2 canonical spellings and placements; approve optional `street2`, `instagram` and `facebook` if preserving these ordinary historical fields is preferred. Leave `other_socials` item shape open pending real examples.

## Optional additions worth considering

- The D6 historical fields are the only suggested payload additions. They are optional, ordinary CV fields with a clear preservation purpose. Do not make them mandatory.
- A raw education-location text companion could enable lossless old-string conversion while retaining city/country, but it adds a field. Prefer a documented conversion failure for 1.3 unless genuine interoperability need justifies this addition.
- Do not add specialized long-CV fields based on length alone. Record concrete missing information first.

## Deferred outside 1.x scope

Profession-specific sections, CV-selection manifests, render/layout controls, a 2.0 redesign, an extension registry, certification branding, an extraction service, and automatic normalization of uncertain dates or legacy project text. `languages[].certificates[]` item type and `other_socials[]` item type need real populated evidence before strict item rules are proposed.
