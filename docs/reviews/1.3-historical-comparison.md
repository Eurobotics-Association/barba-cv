# Barba-CV 1.0 → published 1.2 field comparison (proposal evidence)

**Status:** review evidence for issue [#30](https://github.com/Eurobotics-Association/barba-cv/issues/30). This document does not approve or implement a 1.3 contract. It compares observed artifacts; a template is not a validator.

## Observed conflicts and likely consumer impact

1. **Names and omission.** `Middle_name` becomes `middle_name`; `X/twitter` becomes `twitter`, while `instagram` and `facebook` disappear from named link fields. `street2` also disappears. This may drop data in a template-driven rewrite. `other_socials` could hold social links, but no mapping or item shape is documented. A 1.2 reader expecting only new names may miss old fields; an old reader may miss new names. There is no evidence that the new names were backward compatible in deployed consumers.
2. **Location.** `education[].school_location` is text in A and a `{city,country}` object in B and C. Existing free text such as a campus name or region cannot always be split without interpretation. A strict new object reader would reject old strings; an old string reader would reject new objects.
3. **Projects.** `projects_achievements_extracts` becomes `project_achievements`. A uses an object for `period`, empty arrays for `role`, `sectors`, `competencies`, and `keywords`, and an object for `synonyms`. B uses text for all six fields. C uses the A-like object/array shapes but leaves the arrays empty and `synonyms` empty. The empty arrays prove no item type. A text-only reader fails on C; object/array readers fail on B. The root key rename also breaks readers without aliases.
4. **Skills.** A has empty arrays in all three categories, so its item types are unknown. B shows objects with `name`, `level`, `category`, `keywords`; C uses strings for populated `it_skills` and `soft_skills`. This is an observed 1.2 template/example disagreement, not proof that either is the universal contract. A writer choosing one representation may not work with a reader for the other.
5. **Metadata and extensions.** A has root `parsing_errors` and no version, `meta`, or `extensions`. B and C use `meta.parsing_errors`, `barba_cv_version: "1.2"`, and `extensions: {}`. The schema requires a version, accepts any text as its value, and rejects `extensions` because it omits that property while closing the root. Therefore the published template itself cannot be certified by the published schema.
6. **Validator encoding.** The schema references eight absent definitions: `personalInfo`, `experienceItem`, `educationItem`, `skills`, `certificationItem`, `languageItem`, `projectAchievementItem`, and `stringOrNull`. Its nested field constraints are not executable as published. This is separate from the JSON syntax of the schema and payloads.
7. **Documentation.** [`docs/llm-integration.md`](https://github.com/Eurobotics-Association/barba-cv/blob/b2d3571fae5bbe35e271af4026c59cfc707e9fc1/docs/llm-integration.md) references missing `examples/barba-cv.example.json` and `docs/barba-cv-schema-reference.md`. [`docs/roadmap.md`](https://github.com/Eurobotics-Association/barba-cv/blob/b2d3571fae5bbe35e271af4026c59cfc707e9fc1/docs/roadmap.md) says schema validation is available, which overstates the published artifact given the unresolved references.

## Interpretation and missing evidence

- The stable root grouping (`personal_info`, profile, experiences, education, skills, certifications, languages, interests) is visible in both templates. That supports a conservative 1.3 direction, but does not prove all nested semantics or deployed compatibility.
- The original 1.0 template leaves array item types unresolved, including skills, tasks, achievements, certificates, interests and project lists. Its empty project `synonyms` object does not establish a key/value model. The current repository examples provide later shapes, not proof of original 1.0 item rules.
- Do not promise automatic conversion of names, locations, social links or project data when the source representation does not supply an unambiguous mapping. This is a standard-level compatibility question; application behavior is outside this review.
- Storage, compression and search claims for competing string/object/array shapes need representative data and measurements. None were supplied by these artifacts.
- The declared version should be reported alongside structural matches. Absence of a declaration does not uniquely identify 1.0, because partial payloads can fit more than one version; a literal `"1.2"` does not prove the rest of a payload follows 1.2.
